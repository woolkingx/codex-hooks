Usage

1. Purpose

This chapter is the user-to-Codex operation path. The product characteristic is that codex-hooks is a system for Codex to operate. It solves the permission-management, plugin-capability, and temporary-script boundary problem by letting the human user state the safety, workflow, or development requirement; Codex follows this handbook to update policy data, develop hook features, verify behavior, install hooks, and report evidence.

The normal user interface is not hand-editing rule JSON or memorizing CLI flags. Those artifacts are Codex's operating surface.

user says requirement -> Codex reads handbook -> Codex finds owner/schema/gate -> Codex edits artifacts -> Codex verifies -> Codex installs or reports next action

3. Codex Work Loop

When Codex receives an install, rule, or feature request, it follows this loop:

  1. Read CLAUDE.md, docs/handbook/index.html, and the owning chapters: policy.html, event-model.html, schema-tree.html, deployment.html, and this chapter.
  2. Identify the event owner and official input/output schema. For most command guardrails, start with pre-tool-use.
  3. For rule behavior, update user requirement data first: policy/user.json.
  4. Use the policy CLI or compiler to write the matching runtime rule projection: policy/rules/<event>/<id>.rule.json. The rule id is the filename.
  5. For feature behavior, identify the owning feature module, schema, handler, tests, and handbook gate before editing code.
  6. Run policy sync, rule explain, a focused hook probe for the changed behavior, and the appropriate CI lane.
  7. For install requests, run doctor, render or dry-run install, then apply only when requested.
  8. Report changed files, verification evidence, and remaining warnings.

4. Codex Tool Commands

These commands are the tool surface Codex uses while executing the user's request. They are not the primary product UX. Each command should expose an owner operation; pipeline scripts may compose commands, but should not edit owner files directly.

Current commands:

codex-hooks policy requirements list --file policy/user.json
codex-hooks policy requirements validate --file policy/user.json
codex-hooks policy requirements sync --file policy/user.json --rules policy/rules
codex-hooks policy requirements set deny-example --event pre-tool-use --requirement "Block example command."
codex-hooks policy requirements disable deny-example
codex-hooks policy requirements remove deny-example
codex-hooks policy compile --user policy/user.json --out policy/rules --write

Explain shows which user requirement produced a runtime rule and which trigger paths/features it uses:

codex-hooks policy explain deny-rm --rules policy/rules

Run a hook payload through the same runtime path Codex hooks use:

codex-hooks run test/fixtures/pre-tool-use-bash-rm.json --rules policy/rules

For one-command policy regressions, use a focused probe:

codex-hooks policy verify-command --event pre-tool-use --command "sed -n '1,20p' file 2>/dev/null" --expect allow

5. Install Flow

When the user asks Codex to install codex-hooks, Codex checks before writing. Render prints the Codex hooks.json payload and writes nothing. See deployment.html#codex-hooks-json for the Codex hooks config shape and paths.

codex-hooks render-hooks --target project --rules policy/rules

Doctor checks the local environment, policy sync, schema reachability, and event owner coverage:

codex-hooks doctor --target project --rules policy/rules

Install without --apply returns a dry-run deploy record. Install with --apply writes .codex/hooks.json for the current git project, or $CODEX_HOME/hooks.json for the user target. Codex must report the destination and backup behavior.

codex-hooks install --target project --rules policy/rules
codex-hooks install --target project --rules policy/rules --apply
codex-hooks install --target user --rules policy/rules --apply

6. Logs and Status

Hook stdout must contain only official Codex hook output. Operational observations go to gitignored project-local JSONL logs by default.

codex-hooks run test/fixtures/pre-tool-use-bash-rm.json --rules policy/rules --log logs/codex-hooks.jsonl
codex-hooks logs --log logs/codex-hooks.jsonl --tail 20
codex-hooks status --log logs/codex-hooks.jsonl --tail 1000

Generated hooks.json includes --log "logs/codex-hooks.jsonl" by default; an explicit --log may override it. Fail-closed executor errors are recorded as log error PDU data while hook stdout remains official Codex output only.
