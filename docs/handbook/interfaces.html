External Tool Object Tree

root
  tools.schema
    events
    features
    fn
    system
    help

tools.object_tree -> cli | hook | mcp | web | help renderers

tools.schema is the unified external callable tool set. It is not a CLI command list and not an internal helper registry. It is the public object tree that lets CLI, hook, MCP, web, and help renderers share the same callable capability coordinates.

object fieldmeaningowner boundary
typeCallable object class such as event, feature, fn, system, or help.tools.schema owns external classification.
statusAvailability and stability state for exposure, for example implemented, target, roadmap, hidden, or deprecated.tools.schema owns exposure status, not runtime health truth.
valueDescriptor data: title, owner reference, schema references, gates, adapter visibility, and examples.The descriptor points to owner truth; it does not copy implementation truth.
methodCallable operations such as describe, invoke, verify, render, or list.Methods route to owner modules; adapters only expose them.

Owner Interface Definition

owner owns truth
tools.schema names external callable objects
CLI, hook, MCP, and web expose tool methods
pipeline composes owner operations
CI/CD proves the composed path

CLI commands are stable interfaces over owner modules and tool objects. They may orchestrate owner APIs and collect evidence, but they must not become a hidden service layer. If logic belongs to policy, compiler, runtime, deploy, release, log, status, or a feature owner, the adapter calls that owner instead of reimplementing it.

These commands are implemented owner interfaces. The CLI mutates authoring data first, writes runtime projections through the policy owner, and verifies through the same runtime path used by hooks. Semantic compiler failure, gap, trace, explain, and diagnostic output belongs to log data.

CI Lanes

npm run policy:check   # validate policy/user.json and user-rule sync
npm run policy:smoke   # focused hook probes for policy regressions
npm run verify         # handbook, stale runtime, sync, full tests, smoke

The fast lane proves policy drift and the original symptom. The full lane proves release readiness. This split keeps small policy edits from turning into manual multi-file audits while preserving the fail-closed release gate.

V1 Runtime Rule

V1 has no daemon, no socket, no background state, and no hot reload.
Every hook invocation is a fresh process.
Rules reload at process start.
The manager core must remain daemon-ready.
V1 hook stdout contains only official Codex hook output fields.
