Policy

1. Principle

user requirement data -> compiler -> rule data
input data --(rule data)--> output data

policy/user.json is authoring data. policy/rules/<event>/<id>.rule.json is runtime rule data. Compiler reports, gaps, traces, explanations, and diagnostics are log information.

2. Automation Owner Model

The authoring owner is policy/user.json. Runtime rule files are projections and should be generated, updated, or removed by the policy CLI. A normal policy edit should not require an agent to manually coordinate user policy, runtime rule JSON, focused tests, release worktree files, and CI expectations.

authoring owner: policy/user.json
projection owner: policy compiler / sync writer
runtime reader: src/core/load.mjs over policy/rules
evidence owner: policy sync report + focused hook probe + CI lane

The desired operator loop is: mutate the requirement source, write projections, run a focused runtime probe, then let CI run the broader gate. Manual rule-file edits are allowed for compiler development and emergency debugging, but they must be reconciled through the sync report before deployment.

3. User Requirement Data

{
  "version": "0.0.0",
  "requirements": [
    {
      "id": "deny-rm",
      "event": "pre-tool-use",
      "enabled": true,
      "requirement": "Block Codex from running rm under Bash."
    }
  ]
}

id, event, enabled, and requirement belong here. enabled is user-owned authoring state; missing means true. No rule clause, feature config, runtime config, test, diagnostic, or compiler trace belongs in user requirement data.

4. Requirement to Rule Binding

requirement id = deny-rm
requirement event = pre-tool-use
rule file = policy/rules/pre-tool-use/deny-rm.rule.json

No index file is needed. The rule id equals the requirement id. The event directory names the event. Every runtime rule must have exactly one matching user requirement, and every user requirement must have exactly one matching runtime rule. Runtime rule enabled is a compiled projection of user requirement enabled; after applying the default true, both values must match. If compilation fails, the compiler writes a log record and exits non-zero; it does not create a separate gap artifact by default.

5. Rule Data

Rule data is the persistent compiler output because runtime reads it. The canonical shape is trigger, feature, and output. trigger gives flat official input paths and expected values. feature gives module-owned feature data validated by src/features/<feature>/schema.json. output is official event output data.

{
  "id": "deny-rm",
  "event": "pre-tool-use",
  "priority": 50,
  "trigger": {
    "$.tool_name": "Bash"
  },
  "feature": {
    "bash-command": {
      "value": {
        "path": "$.tool_input.command",
        "name": "rm"
      }
    }
  },
  "output": {
    "decision": "block",
    "reason": "rm denied",
    "hookSpecificOutput": {
      "hookEventName": "PreToolUse",
      "permissionDecision": "deny",
      "permissionDecisionReason": "rm denied"
    }
  }
}

This is the runtime contract: trigger checks official input path values, feature modules interpret derived capability data, and output writes official output data. fields[], conditions[], process, params, and write are not runtime rule data.

6. Block First Time Feature

block-first-time is a stateful feature capability. It is used with another matcher feature such as bash-command: the matcher identifies the tool behavior, and block-first-time decides whether that behavior has already been blocked for the current project/session/compact generation.

scope = normalized cwd + session_id + compact_mark + feature key

first matching tool use:
  mark seen
  emit official block output

later matching tool use in same scope:
  feature no-matches
  later rules may still decide

cwd is the project persistence layer. PostCompact advances compact_mark, so the feature resets after context compaction without deleting old ledger entries. The hook state owner prunes old projects, sessions, compact ids, and seen keys by TTL and size caps.

7. Compiler and Runtime Logs

The following are log information: compile.gap, compiler report, compile trace, explain, diagnostic, and error. They belong under log data, not under policy artifacts or schema roots.

{
  "runtime": "compiler",
  "type": "compile.gap",
  "level": "warn",
  "requirement_id": "semantic-secret-detection",
  "event": "pre-tool-use",
  "message": "Requirement cannot be compiled into current rule data."
}
