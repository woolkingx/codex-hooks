Event Model

1. Definition

An event is a channel name. It owns no fourth schema and no normalized event PDU. Each event runtime has one tuple:

(input schema, rule schema, output schema, executor)

2. Runtime Tuple

partrole
input schemaOfficial Codex hook input data for this channel.
rule schemaEvent-trigger rule data: flat input path values, admitted feature module data, and official output data. It reaches feature and output schemas by $ref.
output schemaOfficial Codex hook output data for this channel.
executorCode that validates input, applies trigger and feature data, validates output, and writes wire output.

3. Rule Data

Rule data is not a match object, not a copied input schema, and not a processor registry. It is an event trigger over input path values plus admitted feature module data.

{
  "id": "deny-rm",
  "event": "pre-tool-use",
  "priority": 50,
  "trigger": { "$.tool_name": "Bash" },
  "feature": {
    "bash-command": {
      "value": {
        "path": "$.tool_input.command",
        "name": "rm"
      }
    }
  },
  "output": {
    "decision": "block",
    "hookSpecificOutput": {
      "hookEventName": "PreToolUse",
      "permissionDecision": "deny",
      "permissionDecisionReason": "rm denied"
    }
  }
}

trigger owns only path-value comparisons. feature owns module capability data. output owns the next-PDU value. Parser-derived values remain feature-private and never become rule fields. Code must not invent intermediate data roots between input schema, rule schema, and output schema.

4. Feature Modules

A feature module owns one capability, its schema, and its handler. Event rule schemas admit feature modules by name. There is no central feature schema root and no free-form feature string syntax.

Feature schemas are referenced schemas, not event tuple members. The event still owns only input schema, rule schema, output schema, and executor. A rule schema may admit rule.feature.<name> by $ref, but that does not create another event layer.

5. Runtime Observations

Errors, compiler gaps, explanations, traces, and diagnostics are log information. Hook stdout still contains only official output data. If an output schema does not admit an error branch, the error is logged and reported out of band.

6. Permission Mode Topology

Codex permission mode changes the event surface. In sandbox or restricted modes, the practical hook surface collapses to PermissionRequest. In full access mode, permission_mode=bypassPermissions, Codex exposes the full hook surface and codex-hooks becomes the local safety manager.

restricted/sandbox mode -> PermissionRequest only
bypassPermissions/full access -> PermissionRequest + PreToolUse + PostToolUse + lifecycle events

Permission mode handling is event-owned, not a uniform global helper. Each event uses the official output fields available to that event: PermissionRequest returns allow/deny, PreToolUse returns block/deny, prompt/tool/stop gates return block when their schemas admit it, and bootstrap events stop with context when their schemas admit only context/stop.

7. PermissionRequest Mode Gate

PermissionRequest remains its own event owner and validates against the official PermissionRequest input/output schemas. Its first job is not policy richness; it is a mode gate. If the incoming permission_mode is not bypassPermissions, the executor returns official PermissionRequest deny output with a message telling the user to restart Codex in full-access mode.

Only after that mode gate passes may the executor project the incoming PermissionRequest input into an internal PreToolUse-shaped SDU, evaluate existing pre-tool-use rules, and map admitted allow/deny results back into official PermissionRequest output.

PermissionRequest input
  -> permission_mode gate
     -> not bypassPermissions: PermissionRequest deny + full-access message
     -> bypassPermissions:
        -> permission-request rules
        -> internal PreToolUse projection
        -> pre-tool-use rules
        -> PermissionRequest output

The projection is not a fourth event schema and not a copied rule file. It is event-owner logic for reusing compatible rule data while preserving the official output boundary. Unmappable PreToolUse results, such as ask/context-only outputs, do not emit PermissionRequest output.
