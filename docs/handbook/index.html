Summary

codex-hooks is moving toward a hook rule compiler plus a deterministic schema-transition runtime. It exists to turn Codex permission-management hell, missing plugin-like capabilities, and temporary development scripts into a user-to-Codex development foundation with schema, owner, and test boundaries. Humans express desired safety, workflow, or feature behavior in natural language; Codex turns that request into policy/user.json requirements, matching rule files, feature modules, verification evidence, and install actions. The hook runtime executes rule data without model calls.

The core event formula is input schema --(rule schema)--> output schema. Rule schema is the event-trigger contract: official input path values trigger module-owned features and produce official output data.

Current implementation uses the canonical data-ontology runtime: event input, event rule, event output, plus system log/status/config/deploy data. Rule data is trigger + feature + output only.

Reader Contract

The handbook is written for three readers at once: a user who needs the product shape, a maintainer who needs the formal contract, and an agent who needs executable boundaries.

Chapter Contract

  1. Principle: the smallest architecture claim the chapter depends on.
  2. Topology: nodes, owners, legal edges, and forbidden crossings.
  3. Formal mapping: SDU, PCI, next-PDU, executor, adapter, or control-plane role.
  4. Worked path: one concrete requirement or hook payload through the owned boundary.
  5. Anti-pattern: the wrong framing this chapter rejects.
  6. Gate: the acceptance rule an agent must prove before closing work.

System Map at a Glance

policy/user.json                         target user requirement source: [{ id, event, enabled, requirement }]
policy/rules/<event>/*.rule.json          executable rule data, one rule per file
schema/codex-hooks.schema.json             root schema graph manifest, reachability only
schema/api/openai-codex/generated/        official upstream input/output schema mirror
schema/tools.schema.json                   external callable object tree
schema/                                   system data schemas: log/status hook-state/config/deploy/profile/tools

src/events/<event>/                       schema transition boundary
   input schema                                 official input pair for this event
   rule schema                                  trigger + feature + output data contract
   output schema                                official output pair for this event
   <event>.mjs                                  executor only: input data -> rule data -> output data

lib/schema2object/                         schema data -> object/fn materialization kernel
src/features/<feature>/                   module-owned feature schema + handler

src/{deploy,status,log}/                   control plane, hook state, and observability
src/adapters/cli.mjs                      transport only

The canonical map: authoring requirement data + event input/rule/output data + runtime log/status/hook-state data + control config/deploy/profile data + external callable tools object tree. Files that do not match this ontology are outside the active system and must be removed before release.
