Policy Automation Optimization

The current architecture has the right source-of-truth split but an expensive operator path. The durable owner is still policy/user.json; policy/rules/<event>/<id>.rule.json remains a compiled runtime projection. The optimization is to remove manual projection work from humans and agents.

policy/user.json
  -> policy owner API
  -> owner-interface CLI
  -> compiler / sync writer
  -> focused policy probe
  -> CI/CD pipeline
  -> release projection

Borrowed operating ideas from mcp-claude-hooks should be adapted, not copied. Useful ideas are a single command surface for external operations, adapters as format converters, schema-backed rule CRUD, hot reload as a later control-plane feature, and test-mode probes that avoid self-blocking while validating deny rules. The rule-file-first model should not be copied because codex-hooks deliberately keeps user requirement data as the authoring owner and official Codex schemas as the output boundary.
