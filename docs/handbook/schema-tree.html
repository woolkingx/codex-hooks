Data Ontology

1. Principle

Schema follows data ontology. If there is no durable or wire-level data object, there is no schema root. A transient computation step, helper function, metadata shortcut, compiler explanation, or diagnostic message is not promoted to a schema because it is JSON-shaped.

data first -> schema second
no data ontology -> no schema root

2. Event Runtime Data

Each hook event owns exactly three runtime data objects.

dataschemameaning
inputofficial Codex input schemaThe hook payload received by the event executor.
ruleevent rule schemaThe event-trigger declaration: input path values, admitted feature module data, and official output data.
outputofficial Codex output schemaThe only data allowed on hook stdout.
 
input data --(rule data: trigger + feature + output)--> output data

3. System Data

System data has schemas because it is durable runtime or control-plane data, not because it participates in an event transition.

dataschemaowner
logschema/log.schema.jsonRuntime observation records: hook events, compiler events, diagnostics, explanations, traces, and gaps all appear as log records.
statusschema/status.schema.jsonRuntime state snapshot and hook control ledger. Status projections are read-only summaries; hook state is writable runtime-local control data.
configschema/config.schema.jsonControl input selecting rule roots, profile, mode, and logging.
deployschema/deploy.schema.jsonControl-plane install or doctor result.
profileschema/profile.schema.jsonOptional persistent runtime selection data.
toolsschema/tools.schema.jsonExternal callable object tree: the public tool set that nests system, event, feature, fn, and help objects as callable descriptors for CLI, hook, MCP, and web adapters.

4. Root Schema Tree

schema/codex-hooks.schema.json owns schema reachability only. It links existing data owners with $ref; it is not event runtime data and does not create a new data ontology.

schema/codex-hooks.schema.json
  api.<event>.input  -> official input schema
  api.<event>.output -> official output schema
  events.<event>.rule -> event rule schema
  features.<name>    -> module-owned feature schema
  system.*            -> log/status/config/deploy/profile/tools/user requirement schemas

The root schema tree is the boundary map: an active schema is reachable from root, and runtime code gets the schema through Loader.resolve(ref). Unreachable schemas are dead or unowned until the handbook names their data ontology.

5. Tools Object Tree

tools.schema is the external callable tool-set root. It owns the public object tree of what can be called from outside the runtime. Event, feature, fn, system, and help objects appear under it as callable nodes. Their local implementation truth remains with the owning object; their external callable identity, adapter exposure, and discovery shape belong to tools.schema.

root
  system.tools -> schema/tools.schema.json
    tools
      events[<event>]
      features[<feature>]
      fn[<fn>]
      system[<system-object>]
      help[<help-object>]

A tool object uses object coding language: type names the object class, status names stability or availability, value carries schema-valid descriptor data, and method lists callable operations such as describe, invoke, verify, or render. Adapters such as CLI, hook, MCP, and web are exits from this tree, not separate sources of tool truth.

6. Hook State Ledger

Hook processes are single-shot. Any feature that must remember a prior hook observation stores runtime-local control state under the status owner, not in event input, rule data, policy authoring data, or logs. The ledger is bounded and disposable: it is allowed to live under the gitignored runtime path and is pruned by TTL and size caps.

hook_state
  projects[normalized_cwd]
    sessions[session_id]
      compact_mark
      processed_compacts[turn_id]
      seen["<compact_mark>:<feature_key>"]

cwd is the project persistence layer because it is the official hook project context. PostCompact advances compact_mark; it does not delete old state. Features scope first-time decisions by session_id, cwd, compact_mark, and feature key, so compaction naturally resets first-time status.

7. Authoring Data

policy/user.json is the authoring plane that receives Codex-authored requirements derived from natural-language input. It is not meant for manual user editing and is not event runtime data. If validated by schema, that schema belongs to the authoring/compiler plane, not to the event schema tuple.

policy/user.json
  requirements[] = { id, event, enabled, requirement }

compiler
  reads requirements
  emits rule data
  writes compile observations to log

9. Gate

GATE-DATA-ONTOLOGY-01: before adding any schema, name the data object, its owner, lifecycle, reader, writer, and reason it cannot be represented as event input, event rule, event output, log, status, config, deploy, profile, tools, or user requirement data.

GATE-SCHEMA-TREE-ROOT-01: every active schema resolves from schema/codex-hooks.schema.json through Loader.resolve(); runtime code does not compose synthetic schemas or bypass returned sub-loader scope.

GATE-TOOLS-OBJECT-TREE-01: a tools.schema node may own external callable identity, adapter exposure, method list, status, descriptor value, schema references, and gates; it must not own event transition logic, feature behavior, policy semantics, runtime state, or deploy side effects.
